# Стек и архитектура реализации прототипа v1

Type: grilling
Status: resolved
Blocked by: 17, 15, 16

## Question

Какой технологический стек и архитектурная граница реализации прототипа v1 обеспечат воспроизводимую доменную модель, журнал событий, исполняемые acceptance-сценарии и минимальный hot-seat UI, при этом не превращая решение в преждевременную production-архитектуру? Нужно зафиксировать runtime, язык и типизацию, тестовый стек, структуру приложения, границы домена/приложения/адаптеров, хранение состояния и событий, а также критерии отказа от текущего нативного JS-стека.

## Answer

### Стек

- TypeScript на Node.js с ESM — канонический язык и runtime доменного ядра, application-слоя и acceptance-тестов.
- Vite — сборка и локальная разработка браузерного прототипа; GitHub Pages — целевой static hosting через GitHub Actions.
- Canvas + HTML/CSS — UI-слой; React/Vue не вводятся в v1.
- Vitest — unit/integration-тесты; Playwright — минимальные browser/acceptance-проверки; `fast-check` — property-based проверки геометрии и инвариантов, если они оправданы покрытием.
- Supabase/PostgreSQL не входит в runtime v1. Он рассматривается как будущий backend для сохранений, replay и затем multiplayer-инфраструктуры.

### Архитектура

Доменное ядро не зависит от DOM, Canvas, Supabase, `Math.random()` и сетевого runtime. Оно принимает команды, состояние и явный RNG-провайдер, возвращая типизированные сериализуемые события и новое состояние либо контролируемый результат отказа. Application-слой оркестрирует команды, журнал и жизненный цикл боя. UI отправляет команды и отображает состояние, события и нормативные предпросмотры.

Состояние UI хранится простым локальным store-фасадом (`getState`, `dispatch`, `subscribe`); Redux/Zustand в v1 не нужны. Persistence задаётся портами `BattleStore` и `EventLogStore`; v1 использует in-memory/local adapter, а будущий Supabase adapter подключается без изменения доменного ядра. Авторизация и backend уже не требуются.

### Геометрия и механики

Axial/cube-геометрия, расстояние, соседи, повороты, supercover-линия и преобразование координат остаются небольшим собственным модулем. Специализированная hex-библиотека не вводится: существующие правила движения, перехвата, тарана и атомарных шагов требуют доменных ограничений, которых generic-пакет не выразит. Отдельные math-библиотеки также не нужны; точность обеспечивается типами, инвариантами и тестами.

## Comments

- 2026-09-27: Решение согласовано: TypeScript/Vite/Vitest/Playwright, Canvas + HTML/CSS, чистое доменное ядро, локальный store, порты persistence и отложенный Supabase adapter; generic hex/math-библиотеки не использовать в v1.
